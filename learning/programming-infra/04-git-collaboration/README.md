# ⭐ 04. گیت و همکاری روی کد

نگارش: ۲۰۲۶-۱۰-۱۰ · پیش‌نیاز: — · بعدی: [05. DevOps، ابر و کانتینر](../05-devops-cloud-containers/README.md)

## چرا مهم است

گیت ابزار استاندارد کنترل نسخه است و بدون آن تاریخچهٔ تغییرات، بازبینی کد و همکاری تیمی عملاً ممکن نیست. تسلط بر شاخه‌ها، ادغام و درخواست ادغام یعنی بتوانید تغییرات را بی‌خطر آزمایش، بازگردانی و منتشر کنید. هر تغییر در گیت ردپای قابل‌پیگیری دارد که پاسخ‌گویی و یادگیری تیمی را ممکن می‌کند. این مهارت در هر پروژهٔ نرم‌افزاری و زیرساختی، از یک اسکریپت کوچک تا پیکربندی ابری، به‌کار می‌آید.

## مفاهیم کلیدی

- **مخزن** (repository): پوشه‌ای که تاریخچهٔ کامل تغییرات آن در پوشهٔ مخفی `.git` ذخیره می‌شود.
- **کامیت** (commit): ثبت یک مجموعه تغییر همراه با پیام توصیفی و شناسهٔ یکتا (hash). هر کامیت به کامیت پیش از خود اشاره دارد.
- **شاخه** (branch): اشاره‌گری متحرک به یک کامیت که کار موازی روی ویژگی‌های مختلف را ممکن می‌کند بدون آنکه شاخهٔ اصلی آسیب ببیند.
- **ادغام** (merge): ترکیب تغییرات دو شاخه. تضاد (conflict) زمانی رخ می‌دهد که هر دو طرف یک بخش را تغییر داده باشند و گیت نتواند خودکار تصمیم بگیرد.
- **بازنویسی یا بازگردانی** (rebase / revert): `rebase` کامیت‌های محلی را دوباره می‌نویسد تا تاریخچه خطی شود و `revert` با یک کامیت معکوس تغییر را لغو می‌کند؛ دومی برای شاخهٔ مشترک امن‌تر است.
- **درخواست ادغام** (pull request): درخواست رسمی برای ادغام یک شاخه، همراه با بحث و بازبینی همکاران پیش از ورود به شاخهٔ اصلی.
- **منطقهٔ آماده‌سازی** (staging area / index): جایی که تغییرات برای کامیت بعدی با `git add` انتخاب می‌شوند؛ این امکان را می‌دهد که کامیت‌ها را کوچک و منسجم نگه دارید.
- **فایل نادیده‌گرفته** (.gitignore): فهرست فایل‌هایی که نباید ثبت شوند، مانند رمزها، محیط‌های مجازی و خروجی‌های ساخت.

## مثال

```bash
git switch -c feature/login
# ... ویرایش فایل‌ها ...
git add app/auth.py
git commit -m "Add login validation"
git push -u origin feature/login
```

یک شاخهٔ جدید برای ویژگی ساخته می‌شود، فقط فایل مرتبط انتخاب و ثبت می‌شود و سپس شاخه به مخزن راه دور فرستاده می‌شود تا درخواست ادغام باز شود. شاخهٔ اصلی دست‌نخورده می‌ماند و بازبینی پیش از ادغام انجام می‌شود. پرچم `-u` شاخهٔ محلی را به نسخهٔ راه دور متصل می‌کند تا دفعات بعد فقط `git push` کافی باشد.

## اشتباه‌های رایج

- کامیت مستقیم روی شاخهٔ اصلی به‌جای کار روی شاخهٔ جدا و درخواست ادغام.
- ثبت رمز، کلید API یا فایل `.env` در تاریخچه. حذف بعدی فایل، آن را از تاریخچه پاک نمی‌کند؛ کلید باید باطل و چرخانده شود.
- پیام کامیت بی‌معنا مانند «fix» که فهم تغییر را در آینده ناممکن می‌کند. پیام باید بگوید چه تغییری و چرا.

## بخش آموزشی و سنجش

### تمرین ۱۰ دقیقه‌ای

یک مخزن آزمایشی بسازید، یک شاخهٔ جدید ایجاد کنید، دو کامیت با پیام‌های معنادار بگذارید و سپس تاریخچه را با `git log --oneline --graph` ببینید. یک بار شاخه را به شاخهٔ اصلی ادغام کنید و نتیجه را در تاریخچه مقایسه کنید.

### سؤال‌های سنجش

- **پلهٔ ۱** (explain): تفاوت `merge` و `rebase` را از نظر تأثیر بر تاریخچه توضیح دهید و بگویید چرا روی شاخهٔ عمومی احتیاط لازم است.
- **پلهٔ ۲** (apply): یک فایل تنظیمات محلی را با `.gitignore` نادیده بگیرید و بگویید اگر آن فایل از قبل کامیت شده باشد چه باید کرد.
- **پلهٔ ۳** (analyze/build): یک تضاد ادغام بسازید، آن را حل کنید و یک قاعدهٔ تیمی برای نام‌گذاری شاخه‌ها و پیام کامیت پیشنهاد دهید که دلیل آن را هم بنویسید.

### معیار ارزیابی

- توضیح `merge` باید بگوید که تاریخچه را حفظ و کامیت ادغام می‌سازد، و توضیح `rebase` باید بازنویسی کامیت‌ها را نشان دهد.
- پاسخ باید تفاوت فایل ردیابی‌شده و فایل نادیده‌گرفته را روشن کند.
- حل تضاد باید هر دو طرف تغییر را بررسی کند، نه اینکه یکی را بی‌بررسی بپذیرد.
- قاعدهٔ پیشنهادی باید دلیل مشخص و قابل سنجش داشته باشد.
- پاسخ باید روش امن‌سازی پس از افشای رمز در تاریخچه (باطل کردن و چرخاندن کلید) را ذکر کند.
