# ⭐ 04. گیت و همکاری روی کد

نگارش: ۲۰۲۶-۱۰-۱۰ · پیش‌نیاز: — · بعدی: [05. DevOps، ابر و کانتینر](../05-devops-cloud-containers/README.md)

## چرا مهم است

گیت ابزار استاندارد کنترل نسخه است و بدون آن تاریخچهٔ تغییرات، بازبینی کد و همکاری تیمی ممکن نیست. تسلط بر شاخه‌ها، ادغام و درخواست ادغام (pull request) یعنی بتوانید تغییرات را بی‌خطر آزمایش، بازگردانی و منتشر کنید. این مهارت در هر پروژهٔ نرم‌افزاری و زیرساختی به‌کار می‌آید.

## مفاهیم کلیدی

- **مخزن** (repository): پوشه‌ای که تاریخچهٔ کامل تغییرات آن در پوشهٔ `.git` ذخیره می‌شود.
- **کامیت** (commit): ثبت تغییرات همراه با پیام توصیفی و شناسهٔ یکتا (hash).
- **شاخه** (branch): اشاره‌گری متحرک به یک کامیت که کار موازی روی ویژگی‌های مختلف را ممکن می‌کند.
- **ادغام** (merge): ترکیب تغییرات دو شاخه. تضاد (conflict) زمانی رخ می‌دهد که هر دو طرف یک خط را تغییر داده باشند.
- **بازنویسی یا بازگردانی** (rebase / revert): `rebase` کامیت‌های محلی را بازنویسی می‌کند و `revert` با کامیت معکوس تغییر را لغو می‌کند؛ دومی برای شاخهٔ مشترک امن‌تر است.
- **درخواست ادغام** (pull request): درخواست رسمی برای ادغام یک شاخه، همراه با بازبینی همکاران.
- **منطقهٔ آماده‌سازی** (staging area / index): جایی که تغییرات برای کامیت بعدی با `git add` انتخاب می‌شوند.
- **فایل نادیده‌گرفته** (.gitignore): فهرست فایل‌هایی که نباید ثبت شوند، مانند رمزها و خروجی‌های ساخت.

## مثال

```bash
git switch -c feature/login
# ... ویرایش فایل‌ها ...
git add app/auth.py
git commit -m "Add login validation"
git push -u origin feature/login
```

یک شاخهٔ جدید برای ویژگی ساخته می‌شود، تغییرات انتخاب و ثبت می‌شوند و سپس شاخه به مخزن راه دور فرستاده می‌شود تا درخواست ادغام باز شود. کار مستقیم روی شاخهٔ اصلی انجام نمی‌شود.

## اشتباه‌های رایج

- کامیت مستقیم روی شاخهٔ اصلی به‌جای کار روی شاخهٔ جدا و درخواست ادغام.
- ثبت رمز، کلید API یا فایل `.env` در تاریخچه. حذف بعدی فایل، آن را از تاریخچه پاک نمی‌کند و کلید باید باطل شود.
- پیام کامیت بی‌معنا مانند «fix» که فهم تغییر را در آینده ناممکن می‌کند.

## بخش آموزشی و سنجش

### تمرین ۱۰ دقیقه‌ای

یک مخزن آزمایشی بسازید، یک شاخهٔ جدید ایجاد کنید، دو کامیت بگذارید و سپس تاریخچه را با `git log --oneline --graph` ببینید.

### سؤال‌های سنجش

- **پلهٔ ۱** (explain): تفاوت `merge` و `rebase` را از نظر تأثیر بر تاریخچه توضیح دهید و بگویید چرا روی شاخهٔ عمومی احتیاط لازم است.
- **پلهٔ ۲** (apply): یک فایل تنظیمات محلی را با `.gitignore` نادیده بگیرید و بگویید اگر آن فایل از قبل کامیت شده باشد چه باید کرد.
- **پلهٔ ۳** (analyze/build): یک تضاد ادغام بسازید، آن را حل کنید و یک قاعدهٔ تیمی برای نام‌گذاری شاخه‌ها و پیام کامیت پیشنهاد دهید که دلیل آن را هم بنویسید.

### معیار ارزیابی

- توضیح `merge` باید بگوید که تاریخچه را حفظ و کامیت ادغام می‌سازد، و توضیح `rebase` باید بازنویسی کامیت‌ها را نشان دهد.
- پاسخ باید تفاوت فایل ردیابی‌شده و فایل نادیده‌گرفته را روشن کند.
- حل تضاد باید هر دو طرف تغییر را بررسی کند، نه اینکه یکی را بی‌بررسی بپذیرد.
- قاعدهٔ پیشنهادی باید دلیل مشخص و قابل سنجش داشته باشد.
- پاسخ باید روش امن‌سازی پس از افشای رمز در تاریخچه را ذکر کند.
