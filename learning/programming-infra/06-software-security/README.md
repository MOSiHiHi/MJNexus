# 06. امنیت نرم‌افزار (مرز با امنیت سایبری)

نگارش: ۲۰۲۶-۱۰-۱۰ · پیش‌نیاز: — · بعدی: —

## چرا مهم است

بسیاری از آسیب‌پذیری‌های بزرگ از خطاهای کدنویسی و پیکربندی ناامن ناشی می‌شوند، نه از حملات پیچیدهٔ پنهان. امنیت نرم‌افزار یعنی ساختن امنیت در مرحلهٔ طراحی و کدنویسی، پیش از آنکه محصول منتشر شود. این حوزه از امنیت سایبری، که بیشتر به دفاع، پایش و پاسخ به حادثه می‌پردازد، متمایز است، هرچند با آن هم‌پوشانی زیادی دارد. هدف این گره رسیدن به عادت‌های امن در کد، داده و وابستگی‌هاست، نه آموزش هک.

## مفاهیم کلیدی

- **اعتبارسنجی ورودی** (input validation): بررسی و محدود کردن همهٔ داده‌های ورودی، از فرم و URL تا فایل و پاسخ API، پیش از استفاده برای جلوگیری از تزریق و خطای منطقی.
- **تزریق** (injection): ارسال ورودی مخرب که به‌عنوان دستور یا کوئری تفسیر می‌شود، مانند SQL injection یا تزریق دستور سیستم‌عامل.
- **احراز هویت و مجوزدهی** (authentication / authorization): تشخیص هویت کاربر در برابر تعیین اینکه چه کاری مجاز است؛ این دو یکی نیستند و هر دو باید بررسی شوند.
- **مدیریت وابستگی** (dependency management): پایش کتابخانه‌های شخص ثالث برای آسیب‌پذیری‌های شناخته‌شده، با ابزارهای تحلیل ترکیب نرم‌افزار (SCA) و به‌روزرسانی منظم.
- **مدل تهدید** (threat modeling): شناسایی دارایی‌ها، مهاجمان احتمالی و نقاط ورود، پیش از نوشتن کد، تا کنترل‌ها در جای درست قرار گیرند.
- **اصل کمترین امتیاز** (least privilege): محدود کردن دسترسی برنامه‌ها و کاربران به حداقل لازم، تا خسارت یک خطا محدود بماند.
- **رمزنگاری و اسرار** (cryptography / secrets): استفاده از کتابخانه‌های استاندارد و پرهیز از ساخت الگوریتم رمزنگاری خانگی، و نگهداری کلیدها خارج از کد.

## مثال

```python
# ناامن: ورودی کاربر مستقیم در کوئری قرار می‌گیرد
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")

# امن: داده جدا از دستور ارسال می‌شود
cur.execute("SELECT * FROM users WHERE name = %s", (name,))
```

در نسخهٔ اول، اگر کاربر به‌جای نام، عبارتی مانند `' OR '1'='1` وارد کند، شرط کوئری تغییر می‌کند و داده‌های بیشتری برمی‌گردد. در نسخهٔ دوم، درایور پایگاه‌داده مقدار را به‌عنوان داده تحویل می‌دهد و هرگز آن را بخشی از دستور تفسیر نمی‌کند، پس همان ورودی فقط یک رشتهٔ معمولی است. نکتهٔ مهم این است که امنیت از جدا کردن داده و دستور می‌آید، نه از فیلتر کردن ظاهری کاراکترها.

## اشتباه‌های رایج

- اعتماد به داده‌های سمت کلاینت، مانند قیمت یا نقش کاربر که در فرم یا کوکی آمده است. همیشه سمت سرور بررسی کنید.
- نصب کتابخانه بدون بررسی نگهداری و آسیب‌پذیری‌های آن، یا غفلت از به‌روزرسانی وابستگی‌ها.
- نمایش جزئیات داخلی خطا به کاربر. پیام خطا باید عمومی باشد و جزئیات فنی فقط در لاگ امن ثبت شود.

## بخش آموزشی و سنجش

### تمرین ۱۰ دقیقه‌ای

یک فرم ساده بسازید که نام کاربر را بگیرد و در پایگاه‌داده ذخیره کند. ابتدا بدون اعتبارسنجی و پارامتر بنویسید، سپس نسخهٔ امن را بسازید و دو کد را کنار هم مقایسه کنید. بنویسید که هر ورودی مخرب احتمالی در هر نسخه چه اثری دارد.

### سؤال‌های سنجش

- **پلهٔ ۱** (explain): تزریق SQL را تعریف کنید و توضیح دهید چرا جدا کردن داده از دستور، این حمله را متوقف می‌کند.
- **پلهٔ ۲** (apply): برای یک API که هر کاربر فقط داده‌های خودش را ببیند، چه بررسی‌هایی لازم است؟ احراز هویت و مجوزدهی را در پاسخ جدا کنید.
- **پلهٔ ۳** (analyze/build): یک مدل تهدید ساده برای سرویس ثبت‌نام بنویسید که دارایی‌ها، سه تهدید احتمالی و کنترل متناظر هر تهدید را مشخص کند.

### معیار ارزیابی

- تعریف تزریق باید مسیر ورود داده ناامن به تفسیر دستور را دربرگیرد.
- پاسخ باید احراز هویت و مجوزدهی را جدا و با مثال توضیح دهد.
- مدل تهدید باید هر تهدید را به یک دارایی و یک کنترل مشخص وصل کند.
- پاسخ باید مرز میان امنیت نرم‌افزار و امنیت سایبری را روشن کند.
- کد امن باید از پارامتر یا ابزار معادل استفاده کند و صرفاً ظاهر ورودی را پاک نکند.
